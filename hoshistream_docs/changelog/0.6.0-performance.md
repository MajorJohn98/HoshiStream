# 0.6.0 — Playback performance, direct play, and a built-in player

## Summary

Playback was addressed on three fronts, and host playback was added: a TorrServer configuration that capped
peer throughput well below the available network capacity, per-request work in the add-on
that repeated expensive filesystem and parsing operations on every HTTP range request, and
the absence of any signal about whether the target device can actually direct play a file.
Both TorrServer settings files were also reconciled, having drifted apart between the
native and Docker deployments.

This covers Phases 1 to 4 of
[plans/2026-08-14-performance-and-cross-platform-plan.md](../plans/2026-08-14-performance-and-cross-platform-plan.md).

## Changes

### TorrServer configuration

Applied identically to `torrserver/config/settings.json` and
`native-data/torrserver/config/settings.json`, which previously disagreed on
`TorrentDisconnectTimeout` (30 native vs 300 Docker).

| Setting | Before | After | Reason |
|---|---|---|---|
| `ConnectionsLimit` | 25 | 200 | The dominant throughput cap. A 25-peer ceiling starves well-seeded swarms. |
| `DisableUpload` | true | false | BitTorrent peers reciprocate; refusing to upload gets the client choked or deprioritized. |
| `PeersListenPort` | 0 | 32001 | Port 0 with UPnP disabled meant no inbound peer connections at all. |
| `EnableIPv6` | false | true | Materially enlarges the reachable peer pool. |
| `TorrentDisconnectTimeout` | 30 / 300 | 600 | With `RemoveCacheOnDrop`, a short pause discarded the cache and forced a cold rebuffer on resume. |
| `ReaderReadAHead` | 95 | 75 | At 95% almost no cache sat behind the playhead, so every backward seek re-downloaded. |
| `CacheSize` | 2 GiB | 4 GiB | Pairs with the lower readahead to keep a real backward window. |
| `PreloadCache` | 25 | 40 | Trades a slightly slower start for a lower chance of an early stall. |

`DisableUPNP` stays `true`: the peer port is forwarded manually so the mapping is explicit.

### Add-on hot paths

- **`local-media.ts`** — `inspectLocalEntry` now caches its result per entry, keyed by a
  selection signature and the source's `mtime` with a 30 s TTL and a 256-entry bound.
  Previously every HTTP range request re-walked the entry's directory tree and issued a
  `stat` per discovered file, so a folder-backed series performed a full directory walk on
  every seek. New `clearLocalInspectionCache(entryId?)` export for tests and invalidation.
- **`local-media.ts`** — media responses now read with a 4 MiB `highWaterMark` instead of
  the 64 KiB default, and set `setNoDelay(true)` on the socket. The default buffer was
  syscall-heavy at 4K remux bitrates.
- **`library.ts`** — `read()` memoizes the parsed library, revalidating against the file's
  `mtime` and size, and `write()` refreshes the cache in place. Previously the entire JSON
  file was read and Zod-parsed on every call, including from inside every range request.
  Callers receive a `structuredClone` so the cache cannot be mutated from outside.
- **`inspection.ts`** — `resolveStreamSource` no longer re-registers a torrent that
  TorrServer already knows. It tries `get(hash)` first and only re-adds on a miss,
  removing a round-trip from the start of every stream request.
- **`inspection.ts` / `metadata.ts`** — new `warmStreamSource` registers a movie's torrent
  when its detail page is opened, so the swarm is already connected by the time the play
  button is pressed. Series already warmed as a side effect of building their episode
  list. Fire-and-forget, deduplicated by entry id, and skipped entirely for local entries.

### Compose

- TorrServer's peer port `32001` is now published on TCP and UDP.
- `mem_limit` raised from 1300m to 2g for headroom against the larger cache.

### Direct-play awareness

`media-probe.ts` already shelled out to `ffprobe`, but nothing acted on the result and it
was never persisted. Most stutter on a TV is not bandwidth — it is the player falling back
to software decoding.

- **`direct-play.ts` (new)** — `assessDirectPlay(probe, homeSpeedMbps)` classifies a file
  as `direct`, `caution`, or `risky` and returns plain-language warnings. DTS, TrueHD, MLP
  and Blu-ray PCM are treated as risky because they are the most common stutter source;
  VC-1 and MPEG-2 rarely have hardware decoding; AV1 and VP9 need a recent device; FLAC,
  Opus and Vorbis are flagged as caution. A verdict is never downgraded from risky to
  caution. The existing 1.5× bitrate headroom check is folded in as a link-capacity
  warning. `directPlayLabel` renders a one-line summary.
- **`types.ts` / `library.ts`** — entries gained an optional `directPlay` field with a new
  `setDirectPlay` writer. It is invalidated alongside `inspectionCache` whenever the source
  or file selection changes.
- **`routes.ts`** — `POST /api/library/:id/inspect?probe=true` now persists the assessment
  and returns it as `directPlay`.
- **`streams.ts`** — stream descriptions carry the warning, so it is visible at selection
  time: `Local • 1 MB • May stutter: dts audio is often software-decoded…`.
- **`assets/manage/views/detail.js`** — the playback panel verdict now reflects codec
  compatibility rather than link speed alone, lists the specific warnings, and adds a
  "Direct play" metric row.

### Cross-platform path safety

Groundwork for the Windows target, and a fix for latent defects on any platform. The
containment guards used `actual.startsWith(root + sep)` and, in one case, a hardcoded
forward slash.

- **`path-safety.ts` (new)** — `containsPath(root, candidate)` and
  `firstSegmentBelow(root, candidate)`, both built on `path.relative`, which handles the
  platform separator and compares case-insensitively on Windows.
- **`local-media.ts`** — `validateBrowserLocalPath`, `isManagedMediaPath`, `saveUpload`,
  and `removeManagedMedia` now use the shared helpers. `removeManagedMedia` previously
  tested `source.startsWith(`${UPLOAD_ROOT}/`)`, which can never match a Windows path, so
  managed media would have been left on disk after entry deletion.

### Host playback (built-in player)

Watching on the machine running HoshiStream no longer needs Stremio or any other add-on
client. See [ADR 0008](../decisions/0008-bundled-mpv-player-over-json-ipc.md).

- **`player-ipc.ts` (new)** — a client for mpv's `--input-ipc-server` protocol:
  line-delimited JSON, replies correlated by `request_id`, asynchronous events fanned out
  to listeners, per-request timeouts, and Zod validation on everything inbound. Malformed
  lines are ignored rather than fatal.
- **`player.ts` (new)** — process lifecycle. Resolves the binary from `PLAYER_PATH`, then a
  bundled `vendor/mpv/<platform>-<arch>/mpv`, then `PATH`. Spawns with a larger demuxer
  buffer (`--cache-secs=60`, `--demuxer-max-bytes=400MiB`) because a swarm needs far more
  buffering than a local file. Falls back to `handOffToSystem` when no binary resolves, so
  playback still works through the OS default handler.
- **`playback.ts` (new)** — resolves a library entry to a play target. **Local entries are
  handed to the player as a filesystem path**, so host playback never touches HTTP, Node,
  or the range-request machinery. Torrent entries use the TorrServer `/play` URL. Observes
  `time-pos` and persists it to the entry (throttled to one write per 15 s), then seeks to
  it on the next play.
- **`types.ts` / `library.ts`** — new optional `playback` field and `setPlayback` writer.
- **`routes.ts`** — `POST /api/player/play`, `POST /api/player/control`, and
  `GET /api/player/status`, all behind the existing bearer auth. `PlayerError` maps to
  `400` with a readable message.
- **`assets/manage/views/detail.js`** — a "Play on this computer" button on the playback
  tab, reporting whether playback was resumed or handed to the system player.

The player deliberately lives in the Node add-on rather than the platform supervisor. The
add-on is already cross-platform, so this works on macOS and Windows now and does not
depend on the supervisor rewrite in the plan.

#### Bug found while testing

The mpv IPC socket path was originally derived from the process id alone. Because a
crashed player leaves its socket file behind, every later start would fail to bind and
playback would be permanently broken until the file was removed by hand. The path now
carries a random per-launch suffix and stale files are removed before binding. Covered by
a regression test.

### Windows vendoring groundwork

- **`packaging/node-lock.json` / `torrserver-lock.json`** — `win32-x64` entries with
  SHA-256 pins, taken from Node's published `SHASUMS256.txt` and computed from the
  TorrServer release asset. The existing macOS Node pin was re-checked against upstream
  and matches.
- **`fetch-node-runtime.mjs`** — handles the Windows `.zip` (which contains `node.exe` at
  the root of the extracted folder) alongside the `.tar.gz` layout (binary under `bin/`),
  and names the output `node.exe` on Windows. It now also deletes the unpacked
  distribution afterwards, which was previously left behind at roughly 150 MB.
- **`fetch-torrserver.mjs`** — writes `TorrServer.exe` on Windows.

## Validation

- `npm run typecheck`, `npm test` (110 passed, 1 skipped — up from 69), `npm run lint`,
  `npm run format:check` — all green.
- `docker-compose config -q` — green.
- New regression tests cover both caches: cache hits, invalidation on file and directory
  change, invalidation on selection change, mutation isolation, and both branches of the
  `get`-before-`add` path. Seven more cover the direct-play classifier, and nine cover
  path containment including the Windows separator and case-sensitivity cases. Fourteen
  more cover the player: IPC request correlation, error replies, event delivery, malformed
  input, connection loss, process spawn and reuse, position reporting, and restart after a
  stale socket.

### Live smoke test

Run against a temporary library with generated fixtures:

- **Range requests are byte-exact.** A `bytes=100-199` request returned `206` with a
  correct `Content-Range`, and the served bytes matched a `dd` of the source by SHA-1.
  Suffix ranges returned `206`, malformed ranges returned `416`.
- **Inspection cache measured at 5.9× on the hot path.** Against a 300-file folder over a
  keep-alive connection, 200 sequential range requests took **2.065 ms/request** with the
  cache disabled and **0.353 ms/request** with it enabled. The old code paid a full
  directory walk plus a `stat` per file on every one of those requests.
- **Direct-play detection end to end.** An H.264 + AAC MP4 classified as `direct` with no
  warnings; a DTS MKV classified as `risky` and the warning appeared in the stream
  description. Both persisted to the library entry.
- **Prewarming is non-blocking and fails safely.** With TorrServer deliberately down, a
  movie meta request returned in 14 ms and the background registration logged a single
  `stream_prewarm_failed` warning without affecting the response.
- **Path guards still hold.** A file inside `MEDIA_ROOT` was accepted (`201`); a file
  outside it and a `../` traversal attempt were both rejected (`400`).
- **The player works end to end against a stub mpv** that speaks the real IPC protocol.
  `play` returned `mode: "mpv"`, and the command log confirmed the player received the
  **local filesystem path**, not an HTTP URL. Pause, seek and stop were all applied and
  reflected in `status`. A seeded position produced `["seek",63.5,"absolute"]` on the next
  play, and an emitted `time-pos` event was persisted to the entry as
  `playback.positionSeconds: 88.25`. Unknown entries, a seek without a value, and
  unauthenticated calls returned `400`, `400` and `401`.
- **Vendoring still works on macOS.** Both fetchers were re-run end to end; the pinned
  Node extracted and reported `v26.3.1`, and TorrServer re-downloaded and verified. The
  Windows zip layout was confirmed against the real archive
  (`node-v26.3.1-win-x64/node.exe`), and `tar -xf` was verified to extract zip archives.

## Notes

- The library and inspection cache-hit tests pin timestamps to whole milliseconds before
  restoring them, because `utimes` does not preserve the sub-millisecond precision that
  APFS reports through `mtimeMs`.
- Deeper TorrServer preloading was considered and deferred. It requires an endpoint that
  is not in the verified subset in `api/torrserver-endpoints-used.md`, and per ADR 0001 it
  cannot be added without checking the running build's Swagger first. The prewarming that
  shipped uses only already-verified endpoints.
